# Архитектура и принятые решения

## Потоки трафика

```text
Internet ── TCP 80 ───────────────> Caddy HTTP-01 / redirect
Internet ── TCP 443 ──────────────> Xray VLESS REALITY
                                           │ ordinary TLS / fallback target
                                           └──> 127.0.0.1:8443 ──> Caddy site
Internet ── UDP 443 ──────────────> Xray Hysteria2
                                           │ invalid/non-client traffic
                                           └──> https://DOMAIN:8443 ──> Caddy site
Panel IP ── TCP 2222 ─────────────> Remnawave Node API
Panel + administrator IPs ─ TCP 22 > OpenSSH
```

Caddy слушает TLS только на loopback `127.0.0.1:8443` и, когда IPv6 реально доступен, `[::1]:8443`. Порт 8443 не открыт в nftables. Caddy на этом внутреннем listener использует HTTP/1.1 и HTTP/2: HTTP/3 отключён, чтобы не публиковать недоступный `Alt-Svc :8443`. Ответы сайта и HTTP-редиректа не раскрывают product-заголовок `Server`. Запись `extra_hosts` контейнера сопоставляет только введённый домен с `127.0.0.1`, поэтому Hysteria proxy masquerade не выходит в публичную сеть и при этом проверяет настоящий сертификат домена.

Перед изменением firewall установщик проверяет публичные `A`/`AAAA` через Google Public DNS-over-HTTPS; системный `dig` используется только при недоступности DoH. Это не позволяет отрицательному кэшу или неисправному DNS провайдера VDS ложно объявить существующий домен отсутствующим. Отсутствие `AAAA` остаётся допустимым IPv4-only режимом, но отсутствие обеих записей или несовпадение опубликованного адреса с адресом VDS является фатальной ошибкой до изменения firewall.

## nftables

Проект владеет только таблицей `inet rw_node_guard`. Обновление происходит одной nft-транзакцией: старая таблица удаляется и новая создаётся в одном batch. Нет `flush ruleset`, поэтому таблицы Docker и Remnawave Node Plugins сохраняются.

Base chain `input` имеет policy `drop`. До публичных правил принимаются loopback, `established,related`, DHCP replies и обязательные управляющие ICMP/ICMPv6 сообщения. Echo IPv4 ограничен по частоте; ICMPv6 не блокируется, поскольку без Neighbor Discovery и Packet Too Big корректный IPv6 невозможен.

Установщик не создаёт base chain для `forward`: Node использует host networking, а управление пересылаемым трафиком остаётся за Docker и Remnawave Node Plugins. Отдельный `forward` с policy `drop` мог бы перекрыть разрешения из их собственных таблиц. `output` разрешён: Node, ACME, DNS и обновления должны выходить в сеть.

Кандидат сначала существует только в root-only `/run`. Для каждой попытки создаются уникальные неизменяемые snapshot и systemd rollback на три минуты. Установщик требует открыть **новую** SSH-сессию и явно ввести `yes`; без TTY правила всегда откатываются. Только после подтверждения кандидат атомарно становится постоянным и сервис включается. SSH, Docker и Caddy имеют `Requires=` на firewall, поэтому ошибка его загрузки не открывает административные демоны. Активный или включённый сторонний firewall на входе приводит к отказу, а не к его молчаливому отключению. Стандартный `nftables.service` остаётся выключенным после commit, чтобы `/etc/nftables.conf` с возможным `flush ruleset` не стирал таблицы плагинов.

## Caddy и сертификаты

Caddy использует HTTP-01, потому что публичный TCP 443 принадлежит REALITY. Admin API отключён: host-network контейнер не должен управлять Caddy через loopback. Сертификаты остаются в отдельном Caddy storage. Root-сервис каждые 30 минут считывает ограниченный объём данных из Caddy-owned каталога **от пользователя caddy** в неизменяемые root-временные файлы. Уже эти копии проверяются по SAN, сроку, системной цепочке доверия и соответствию private key, затем публикуются с mode `0600`. Так root не следует изменяемым Caddy symlink/path после проверки. Node перезапускается только при реальном изменении сертификата.

Сайт генерируется детерминированно из случайного seed. Повторный install сохраняет существующий сайт, команда `regenerate-site` создаёт новый. Все шрифты обслуживаются локально.

## Производительность

Профиль `small`, `medium` или `large` определяется по RAM и CPU. Настройки увеличивают backlog, conntrack и допустимые autotune-границы, но не резервируют весь указанный объём памяти под каждый socket. BBR+fq включаются только если ядро сообщает поддержку. RPS включается лишь для машин минимум с четырьмя CPU и максимум двумя RX queues — это помогает простым виртуальным NIC и не вмешивается в многоканальные NIC выделенных серверов.

Существующий swap никогда не изменяется. Если swap отсутствует, создаётся умеренный 1–2 GiB `/swapfile`; существующий неактивный файл не перезаписывается.

## Обновления и отказ

Timer ежедневно получает `remnawave/node:latest`. Перед recreate текущий image digest получает локальный rollback tag. Новая версия должна запустить контейнер, Node API и все ранее работавшие публичные listeners. Иначе старый digest возвращается под `latest`, контейнер пересоздаётся, а неудачный digest запоминается до появления следующего образа.

Это защищает от явного crash/startup regression, но не доказывает семантическую совместимость протокола или доброкачественность образа. Успешные digest записываются в root-only журнал. Следование `latest` остаётся осознанным supply-chain риском: host-network и `NET_ADMIN` делают доверие publisher/registry существенным. Поэтому автоматическая перезагрузка ОС отключена, а журналы и `rw-node diagnose` остаются частью эксплуатации.
